# Async一括停止の完了カウンター

2026-10-18。公開APIを維持し、Async一括停止がHandleごとの終了TaskとTask.WhenAllを作る方式から、一括停止ごとの完了カウンターと終了Taskを持つ方式へ変更した。

## 実装

停止対象のスナップショットを確定して停止要求を出した後、未完了のHandleだけを待機対象として登録する。Handleの終了状態が確定した時点でEngineへ通知し、そのHandleを待っている各一括停止のカウンターを進める。完了理由によらず最後の対象が終了すれば完了する。これにより通常のフェード終了だけでなく、個別StopやEngine破棄でも待機を解除する。

登録リストはEngine内で再利用し、Handleからの終了通知で辞書から取り除いてから通知する。再入中は通知中のリストをプールに返さず、すべての通知後にClearして返す。同じHandleを複数の一括停止が待つ場合も個別のカウンターを保持する。公開StateChangedには内部の待機処理を購読しない。

個別HandleのWaitForCompletionAsyncは従来どおり独立して利用できる。Tokenは待機だけを取り消し、停止・フェードは継続する。キャンセルされた一括停止の内部登録は、停止対象が終了すると解放される。即時終了や空対象では一括停止用のカウンターもTaskも生成しない。

## 同条件の再測定

Unity 6000.3.10f1 / Windows Editor Play Mode / Mono / i5-12400F。Deep Profiling無効、クリーン再コンパイル後。生成1秒mono44.1kHz Clip、16／64／128音、同数のSourceプール。ウォームアップ16回後、GC.AllocはメインスレッドのProfilerMarker配下を16回×3、バッチCPUは16回×5の中央値。4096B配列4128B／空処理0Bの校正とフレーム進行を各実行で確認。

バッチはN回のPlay、フェード付き停止要求、明示的なTick1回によるフェード完了を含む。完了したバッチTask群をまとめて待つ処理は計測外。別スレッドの継続処理のCPU・Alloc、DSP、発音遅延は含まない。

## 回帰確認

関連69ケースがPlay Modeで成功（GroupStopTests23、AudioEngineTests33、PlaybackCompletionTests5、PlaybackStateChangedTests8、スキップなし）。新規6ケースでは、重複する一括停止それぞれの最後の対象、片方だけのキャンセル、Engine破棄、個別完了待機との併用、フェード通知からの重複停止、通知中の即時停止により外側も即座に完了する場合を確認した。既存ケースでAll／Category／Owner／Library、追加再生の除外、ロード中の停止、待機と通知の順序を検証した。実行はPipelineの簡易ランナー。

2022.3.62f3／6000.2.9f1のEngine参照によるRuntime条件付きコンパイルも成功。既存の未代入シリアライズフィールド等の警告は残る。旧Editorでの実行・IL2CPPでの検証は未実施。

## 残る費用

一括停止ごとのカウンター・TaskCompletionSource・Taskなど880Bは残る。Tokenがキャンセル可能ならAsyncWaitの登録やラッパーも別途発生する。初回、同時に待つHandle数の増加、重複する待機数の増加では辞書・登録リストの確保や容量拡張があり、今回の880Bはウォームアップ後の値。リストの内部容量はEngineが保持するが、終了後はHandleのキーと待機オブジェクトの参照を外す。

今回は待機コストを集約し、公開Handleのプール化・再利用APIや、フェード制御自体の仕様変更は導入していない。実際のI/O・DSP・Player・長期のキャッシュ容量推移は引き続き測定対象として残る。
