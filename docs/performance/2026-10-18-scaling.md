# 同時再生スケーリングとLibrary反復測定

追記：Loader履歴の強参照は[弱いキーへの移行](2026-10-18-library-weak-history.md)で解消済み。Asyncフェード停止も[完了カウンターへの集約](2026-10-18-batch-completion.md)で待機追加分を880B/バッチへ削減済み。以下は修正前の測定記録。

2026-10-18。今回は測定用スクリプトとレポート・TODOだけを追加し、Runtime実装は変更していない。結論は、TickのAllocより先に、解放済みLoaderを選択履歴が保持し続ける問題を直すべき。

## 条件

Unity 6000.3.10f1 / Windows Editor Play Mode / Mono / i5-12400F。Deep Profiling無効、クリーン再コンパイル後。生成した1秒のmono 44.1kHz Clip、同時再生16／64／128、同数のAudioSourceプールを事前生成。設定上のReal Voicesは32、Virtual Voicesは512。64／128音はすべてが実発音していることを意味しない。DSP処理・ミックス・発音遅延は測定していない。

EngineDriverを無効にして、作成済みのTickデリゲートを明示的に呼ぶ。反射呼び出しは測定ループ内に入れない。CPUはProfiler記録無効のStopwatch、128回×5の中央値（バッチは16回×5）。ウォームアップ16回。GC.Allocは別のProfilerMarker内を16回×3で採取し、メインスレッドの配下だけを集計する。非同期コールバックの別スレッドでの確保・CPUは含まない。4096B配列4128B／空処理0Bの校正とフレーム進行を各実行で確認した。

## CPU中央値（μs/操作）

| 操作 | 16音 | 64音 | 128音 |
|---|---:|---:|---:|
| Tick.TwoD | 2.307 | 8.202 | 16.927 |
| Limits.Engine.Reject | 5.663 | 5.723 | 7.366 |
| Limits.Engine.Replace | 15.075 | 18.005 | 23.015 |
| Limits.AllScopes.Replace | 20.199 | 37.779 | 56.958 |
| Tick.Attached.Moving | 6.584 | 32.451 | 59.280 |
| Batch.PlayAll.StopAll.Fade.Tick | 267.694 | 1235.713 | 3460.050 |
| Batch.PlayAll.StopAllAsync.Fade.Tick | 458.919 | 2037.931 | 4548.869 |

Tick.TwoDは追従なし、Tick.Attached.Movingは共通のTransformを毎回動かして全音源へ追従させる。Engine.Rejectは上限到達時の要求拒否、Engine.Replaceは全体制限だけの置換。AllScopes.Replaceは全体・Category・Sound・Ownerの4制限を設定した同一Soundの置換。置換中も同時再生数が一定であることを確認した。

バッチ操作はN回のPlay、フェード付き停止要求、1回のTickによるフェード完了を含む。StopAll単独のCPUではない。Async版のWhenAll完了はCPU計測の外で待つため、表は待機完了までの壁時計時間ではない。バッチ後は再生中・ロード待ちが0であることを確認した。

Tickと追従更新は0B。制限到達時の要求拒否は424B、置換は632Bで音数によらない。同期フェードバッチはちょうど632×N Bで、Play以外の追加Allocは今回の条件では0B。Asyncフェードバッチは128音で200,084B、同期版との差119,188B。Handleごとの終了待機・集約処理の費用が残る。

## Libraryのロード・解放を500回反復

同一の生成Libraryを使い、①同じLoaderを再利用、②毎回新しいLoaderを利用者側でDispose、③SoundLibraryReferenceのFactoryから毎回新しいLoaderを生成しEngine側でDispose、の3通りを実行。1回ごとにPreload→Play→Stop→Preload解放を行う。10／100／500回目にロード・再生中と解放後を記録し、Engine破棄後も記録する。Force GC後のEditor全体のManaged／Mono／Total Allocated／Reservedと、Engine内の保持数を保存した。

| 条件 | 履歴数 10回後 | 100回後 | 500回後 | Dispose済みLoader 500回後 | Engine破棄後の履歴 |
|---|---:|---:|---:|---:|---:|
| 同じLoader | 1 | 1 | 1 | 0 | 0 |
| 新しいLoader | 11 | 101 | 501 | 500 | 0 |
| Reference Factory | 11 | 101 | 501 | 500 | 0 |

履歴数にはウォームアップのLoader1件を含む。ロード・再生中はSession／SharedLibrary／再生／リースが各1、解放後はすべて0、通常のSourceプールは1を保持する。Engine破棄後のプール数は0。各サイクルでリース・Session・再生が0へ戻ることも検査している。

一方、librarySelectionsのキーがISoundLibraryLoaderへの強参照であり、毎回異なるLoaderを使うと履歴が1サイクルに1件増える。Force GC後もDispose済みLoader500件がEngineから参照される。Reference Factory経由でも再現した。これは未完了のロードやリースの残留ではなく、選択履歴の寿命による保持。Engine.Disposeで履歴のキー参照は消えるが、Dictionary内部容量やEditor全体のメモリが即座に減ることは保証しない。

総メモリは約800MiBのEditor全体に測定スクリプトやProfiler等も含み、変動・丸めがある。差分をLoader単体の正確なバイト数やNativeメモリ漏れのサイズとは扱わない。Clip／Libraryはハーネスが保持したままなので、実際のAddressables／ResourcesのI/OやClipのNativeアンロード・ピークメモリを検証したものでもない。今回確定した問題は、履歴の強参照とその件数の増加である。

## 次の優先順位

1. librarySelectionsがLoaderを不必要に延命しないよう寿命を整理する。同じLoaderが生存する間のSequence／Shuffle履歴、再ロード、共有Libraryを維持して修正し、Factory経由の反復で再測定する。弱いキーや安定したLibrary識別子の利用を比較し、APIの変更は別途判断する。
2. 多数のAsyncフェード停止の待機費用を調査する。128音で同期版との差が約116.4KiB/バッチ。キャンセルと再入を保ちつつ、Handleごとの終了Taskが必須か検討する。
3. Tick・追従のCPUは128音で約17／59μsであり、今回のEditor条件では上の2点より低優先。制限走査の索引化は大量のPlay頻度やPlayerでの結果を見て判断する。
