# AudioOrbit 再生APIのベースライン測定

2026-10-18。再利用可能なAudioPlaybackへ変更する前の現行実装を測定した。ランタイム実装の最適化は行っていない。

## 環境と方法

- Unity 6000.3.10f1、Windows Editor Play Mode / Mono、Intel Core i5-12400F。
- Deep Profilingを無効化。CPU時間測定中はProfilerの記録も無効化し、GC計測時だけCPU記録を有効化した。元のProfiler設定は測定後に復元した。
- 1秒、44.1kHz、モノラルの生成済みAudioClip、Clip数1、ループ再生。AudioSourceプールと同時再生上限は1。1音ずつ開始して停止する。
- 各条件128回のウォームアップ後、CPU時間は512回×7試行。Engine取得・通知の個別測定・校正は4096回×7試行。表は1操作あたりの中央値。
- AllocはCPU時間と別に128回×3試行。固有ProfilerMarker配下のメインスレッドのGC.Allocメタデータを合算した。フレーム全体のEditor／ゲーム側の確保は含めない。
- この環境のGC.GetAllocatedBytesForCurrentThreadは、4096バイト配列を確保しても差分0を返したため不採用。最初の0Bという結果は破棄した。Unity Profiler側では配列1個4128B、空操作0Bを確認してから本測定した。
- 測定前後にフレーム数が17410→18129と進行したことを確認。ユーザーのシーン／アセットを保存・変更していない。測定用Engine・Clip・Library・Contextは終了時に破棄した。

## 結果

「再生→停止」は両操作を合わせた1回。「Pause→Resume」は2遷移を合わせた1回。時間とAllocは別の試行で取得しており、空操作の時間は差し引いていない。

| 条件 | Alloc / 操作 | 中央値 µs / 操作 |
|---|---:|---:|
| 空操作（測定器の対照） | 0 B | 0.006 |
| 登録済みKeyで再生→停止、購読なし | 2,984 B | 20.190 |
| 保持済みDirectSoundReferenceで再生→停止、購読なし | 3,428 B | 20.439 |
| 事前ロード済みISoundLibraryReferenceで再生→停止、購読なし | 3,496 B | 26.822 |
| 登録済みKeyで再生→Pause→Resume→停止、購読なし | 3,064 B | 20.767 |
| 同操作、購読者1人、通知のキュー投入まで | 3,448 B | 23.228 |
| 登録済みKeyで再生→StopAll、購読なし | 4,489.125 B | 29.684 |
| 登録済みKeyで再生→停止→完了済み結果のWaitForCompletionAsync | 3,344 B | 24.113 |
| OrbitContext.Get、Engine作成済み・定義1件 | 220 B | 1.026 |
| 保持したHandleでPause→Resume、購読者0人 | 80 B | 0.569 |
| 保持したHandleでPause→Resume、購読者1人・通知実行込み | 416 B | 1.527 |
| 保持したHandleでPause→Resume、購読者8人・通知実行込み | 528 B | 1.902 |

通知実行込みの3条件は、確保済みバッファを持つ専用SynchronizationContextをHandle作成時だけ指定し、キューを同じメインスレッドで明示的に処理した。通知生成・GetInvocationList・購読者呼び出しを含むが、UnitySynchronizationContext固有のキュー処理コストは含まない。購読者は同じ静的コールバックで、ユーザーコードのAllocは発生させない。

実際のUnitySynchronizationContextを使う「購読者1人・キュー投入まで」の条件では、購読前にPlayingとなるため通知対象はPaused・Playing・Endedの3回。登録した全通知が処理されたことも検証した。後続フレームのGetInvocationListによるAllocはこの条件の数値には含まない。

事前ロード済み参照は、メモリ上のLibraryを返す測定用Loaderを使用し、リースを保持する。Resources／Addressables固有のロード・依存解決・I/Oを測った数値ではない。

## 判断

1. **まず通知経路を最適化する。** 購読者なしでもPause→Resumeに80B、つまり1遷移40B発生した。GetInvocationListだけでなく、早期return前に確保され得るクロージャも調査対象。購読者1人で1遷移208B、8人で264B（いずれも専用キューでの配信込み）だった。購読一覧のキャッシュと通知エンベロープ／デリゲートの再利用を検討する。
2. **既存Engine取得の高速経路を作る。** 定義1件・取得済みでも220B/回。毎回の定義検証・HashSet生成を避ける余地がある。Editorで定義が変わった場合のキャッシュ無効化は必要。
3. **再生要求全体のAllocを分解する。** 最も単純な再生→停止でも約2.98KB/回。Directはさらに444B、事前ロード済み参照経路は512B増えた。HandleだけでなくTaskCompletionSource・CTS・一時コレクション・設定コピーなどの内訳を次に計測する。再利用可能なAudioPlaybackだけでこの全量を削減できるとは判断しない。
4. **非Async一括停止の待機処理を見直す。** 対象1音でもStopAll経路はHandle.Stopより約1.5KB/回多い。現在は非Async版もTask・待機リストを作る経路を通る。停止対象の安全なスナップショットと通知の再入安全性を維持して改善する。
5. **待機Taskの遅延生成を比較する。** 完了済み結果を待つ呼び出しでも、この条件では360B増えた。未完了待機・CancellationToken付き待機・再生世代の切り替えは別途測定する。

再利用可能なAudioPlayback版は未実装・未測定なので、新APIの優劣や削減率はまだ比較できない。まず現行APIの低リスクな改善を独立に測定し、その後プロトタイプと同じ条件で比較する。

## 測っていないもの

IL2CPP／Standalone Player／WebGL、実際のAddressables・Resourcesロード、音が聞こえるまでの遅延、DSP処理時間、同時再生数増加時の制限判定・追従Tick、LoopRegionClipのPCMコピーとピークメモリ、長時間運用時の残留メモリは対象外。CPU値はEditorのこのマシンの参考値であり、製品Playerへの性能保証には使わない。

## 再実行

スクリプトは[Tools/Benchmarks/AudioOrbitBaseline.cs](../../Tools/Benchmarks/AudioOrbitBaseline.cs)、各試行の生データは[JSON](2026-10-18-baseline.json)。UnityをPlay Modeにし、Deep Profilingを無効化して実行する。計測終了後は元の設定／モードに戻す。スクリプト自身はProfiler記録の有効状態とCPU記録設定を復元する。

```powershell
unity command run_script --file Tools/Benchmarks/AudioOrbitBaseline.cs --args '["docs/performance/2026-10-18-baseline.json"]' --timeout_ms 55000 --timeout 60 --caller plugin --skill unity-cli --project-path D:/git/AudioOrbit --format json
```

この校正値4128Bは今回のランタイムの配列ヘッダー込みの値。別ランタイムで校正が失敗したら、0Bなどを結果として採用せず計測手段と期待値を確認する。
